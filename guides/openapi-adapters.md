# OpenAPI Adapters

An API reference belongs in a documentation site, but where the OpenAPI
document comes from varies enormously. It might be derived from Ash resources,
declared with OpenApiSpex, generated by a Go service, or written by hand and
committed. DocShell does not care which — it asks an adapter.

## Choosing an adapter

Three ship with the package.

### Ash domains

If the API is built with Ash and AshJsonApi, the description already exists in
the resource definitions. [AshOaskit](https://hexdocs.pm/ash_oaskit) turns them
into an OpenAPI document:

```elixir
config :doc_shell,
  open_api_adapter: DocShell.Generate.OpenApi.Adapters.AshOaskit,
  domains: [MyApp.Blog, MyApp.Accounts],
  title: "My API",
  api_version: "1.0.0"
```

Add `{:ash_oaskit, "~> 0.3"}` to the host's dependencies. It is optional to
DocShell and resolved at runtime, so projects that do not use Ash never pull it
in.

AshOaskit options DocShell knows nothing about pass through `:open_api_options`:

```elixir
config :doc_shell,
  open_api_options: [version: "3.0", resource_scope: :routed]
```

See `DocShell.Generate.OpenApi.Adapters.AshOaskit`.

### An existing OpenApiSpex module

Phoenix applications that already describe their API with
[OpenApiSpex](https://hexdocs.pm/open_api_spex) have a module exporting
`spec/0`. Point at it rather than describing the API twice:

```elixir
config :doc_shell,
  open_api_adapter: DocShell.Generate.OpenApi.Adapters.OpenApiSpex,
  open_api_options: [module: MyAppWeb.ApiSpec]
```

The adapter round-trips the struct through the library's own JSON encoder, so
the artifact matches what the application serves over HTTP.

See `DocShell.Generate.OpenApi.Adapters.OpenApiSpex`.

### A file or a map

For everything else — hand-written documents, output from another language's
toolchain, a spec vendored from another repository:

```elixir
config :doc_shell,
  open_api_adapter: DocShell.Generate.OpenApi.Adapters.RawJson,
  open_api_options: [path: "priv/openapi.json"]
```

Or pass a map directly, which is mostly useful in tests:

```elixir
DocShell.Build.run(
  open_api_adapter: DocShell.Generate.OpenApi.Adapters.RawJson,
  open_api_options: [spec: %{"openapi" => "3.1.0", "info" => %{}, "paths" => %{}}]
)
```

See `DocShell.Generate.OpenApi.Adapters.RawJson`.

### None

Leaving `:open_api_adapter` unset is a supported choice, not an omission. The
build emits a valid empty OpenAPI 3.1 document, so `openapi.json` is always
present and a renderer never has to handle its absence.

## Writing your own

One callback:

```elixir
defmodule MyApp.Docs.GatewaySpec do
  @moduledoc "Loads the published API description from the gateway's cache."

  @behaviour DocShell.Generate.OpenApi.Adapter

  @impl true
  def load(opts) do
    path = Keyword.fetch!(opts, :cached_spec_path)

    with {:ok, json} <- File.read(path),
         {:ok, document} <- Jason.decode(json) do
      {:ok, document}
    else
      {:error, reason} -> {:error, {:gateway_spec_unavailable, path, reason}}
    end
  end
end
```

```elixir
config :doc_shell,
  open_api_adapter: MyApp.Docs.GatewaySpec,
  open_api_options: [cached_spec_path: "priv/gateway/openapi.json"]
```

### What `load/1` receives

The build's options merged with `:open_api_options`, the latter winning:

| Key | Source |
| --- | --- |
| `:domains` | `config :doc_shell, :domains` |
| `:title` | `config :doc_shell, :title` |
| `:api_version` | `config :doc_shell, :api_version` |
| `:security_schemes` | `config :doc_shell, :security_schemes` |
| anything else | `config :doc_shell, :open_api_options` |

Ignore the keys that mean nothing to your source.

### What to return

`{:ok, document}` where `document` is a map with an `openapi` key of `"3.0.x"`
or `"3.1.x"`, or `{:error, reason}`.

Make the reason worth reading — it appears in a failed build with no other
context, so `{:gateway_spec_unavailable, path, :enoent}` earns its keystrokes
over `:error`.

### Depending on optional libraries

An adapter that needs a library the host may not have installed should check at
runtime rather than referencing it at compile time:

```elixir
defp build_spec(opts) do
  if Code.ensure_loaded?(SomeSpecLibrary) and function_exported?(SomeSpecLibrary, :spec, 1) do
    {:ok, SomeSpecLibrary.spec(opts)}
  else
    {:error, :some_spec_library_not_available}
  end
end
```

A compile-time reference produces an undefined-module warning in every project
that does not install the library — and with `--warnings-as-errors`, a broken
build. This is what lets DocShell ship AshOaskit and OpenApiSpex adapters
without depending on either.

## What DocShell guarantees

`DocShell.Generate.OpenApi.extract/2` sits between the build and code it does
not own. It checks the adapter exists and exports `load/1`, calls it inside a
rescue so a raising adapter yields a reason rather than a stacktrace, and
verifies the result claims to be OpenAPI 3.0 or 3.1.

That last check is shallow on purpose. Full schema validation belongs to the
library that produced the document, and duplicating it here would mean DocShell
rejecting documents its own adapters consider valid. What it catches is the
common integration mistake: an adapter returning a config map, an envelope, or
a struct that was never rendered.

Errors you may see:

| Error | Cause |
| --- | --- |
| `:invalid_adapter` | The module does not export `load/1`. |
| `:invalid_openapi_source` | The adapter returned neither `{:ok, map}` nor `{:error, reason}`. |
| `:invalid_openapi_document` | No usable `openapi` version key. |
| `{:openapi_adapter_failed, message}` | The adapter raised. |

Anything else came from the adapter itself.
